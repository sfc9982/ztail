# Security policy

## Status and scope

ztail is pre-release. Security fixes are best-effort; there is no promised response
time or long-term support policy yet. Use a current reviewed revision. The project
is MIT-licensed; release publication still requires maintainer review and approval.

Relevant boundaries include compressed-data parsing, decompression amplification,
resource consumption, file rotation/replacement, filename diagnostics, terminal
control sequences, generated shell scripts, and the release supply chain.

## Reporting a vulnerability

Do not attach production logs, credentials, personally identifying information,
or a working exploit to a public issue. If GitHub private vulnerability reporting
is enabled for this repository, use **Security -> Report a vulnerability**.
Otherwise open an issue containing only a request for a private reporting channel;
wait for a maintainer to provide one before sharing details. No unverified email
address or nonexistent reporting service is assumed here.

Include the output of `ztail --build-info`, OS/kernel, a minimal synthetic sample,
exact command, expected/actual behavior, and potential impact. State whether the
problem requires following, concurrent rewrites, a terminal, or redirected output.
Keep dangerous samples clearly labeled and reproducible without elevated access.

## Known limitations are not security guarantees

- Only regular files are accepted; no stdin/FIFO/socket/device streaming.
- Decoding and follow work are bounded in steps, but a large --lines value or many
  operands can still consume substantial memory. A blocked output can block the
  process; there is no hard process-wide memory or execution-time quota.
- Log bytes are not sanitized. They may contain ANSI/OSC sequences. --color never
  only disables ztail's UI colors, not control sequences inside the log.
- Concurrent rewriting is not an atomic snapshot. Some unflushed compressed data
  cannot be displayed until the writer emits it. See README for format semantics.
- Completion scripts must be generated by a trusted binary before sourcing.
- Checksums detect corruption, not publisher identity. Draft releases require
  manual review; no automatic self-update or privileged network installer exists.

## Dependency maintenance

A read-only GitHub Actions workflow runs cargo-audit on dependency changes and
weekly against RustSec's advisory database. Dependabot proposes Cargo and action
updates; merging remains manual and requires MSRV/default/zstd tests. Workflow
actions are pinned to full commit SHAs. Findings must be assessed: absence of
known advisories is not proof of safety. This job checks RustSec advisories, not
registry yanking status. The audit does not replace fuzzing,
parser tests, dependency license review, or review of newly introduced unsafe code.
